# RailroaderRV 1.0

RailroaderRV 是本项目面向 Railroader 的正式房车模组，当前产品版本为 1.0。模组目录、
Mod ID、Lua 命名空间和物品 full type 均使用 `RailroaderRV`。`mod.info` 中的 `modversion=1.0`
是产品版本；ModData schema 版本由 Lua 常量单独管理，两者不可混用。

## 模块与接口索引

模块边界和静态代码分析见[全局模块索引](docs/module-analysis/global-summary.md)。分析文档是静态
审计记录；运行时行为和当前接口以本 README 与 `contents/mods/RailroaderRV/42/` 下的代码为准。

## 设计与安全边界

路线和房屋由服务端按需程序化生成，不内置地图。客户端只提交操作意图；服务端验证玩家、
权限、请求阶段和当前存档身份，负责世界修改和同步。

生成候选区从默认锚点 (20050,2050,0) 开始，按 5 行（Y）×20 列（X）排列；每格为一个
半开区间 100×100 管理区域，首格 x=[20000,20100)、y=[2000,2100)。服务端只从当前
Mapping 未占用的格子中按行优先顺序分配。Mapping 持久记录保存 slotIndex，anchor 与范围按
slotIndex 派生。生成先将客户端和服务器移到由所选布局中心派生的 staging 位置，再等待目标 IsoCell
可用并校验坐标；等待期间不做世界修改。Construction 先遍历完整管理范围，清理当前 cell 已有 square
上的对象，然后只在固定模板对象的宿主 square 创建模板内容，缺失的宿主 square 按需创建；不铺整片金属
地板，也不填满空白格。完成生成和客户端最终位置确认后才提交 Mapping；首格的 FinalRelocate 点为
`(20050.5,2050.5,0)`，其他格按该格 anchor 平移。

**当前失败边界**：生成事务没有持久回滚记录或世界对象 undo ledger。清理或构建失败可能留下已执行的世界
修改，下一次尚无 Mapping 的请求会先对管理范围重新执行完整清理，再尝试生成。这与根目录
`agents.md` 的服务端失败回滚约束存在未解决差异；本 README 如实记录现状，不表示该差异已验收或获准保留。
矩阵空闲只表示 Mapping 未占用，不代表地图区域为空。
生成时客户端以“正在生成房车”提示等待。临时 staging 点由当前管理区中心计算：
`managedOriginX+floor(width/2)`、`managedOriginY+floor(height/2)`、`-15`。`-15` 是只存在于进程内存中的无状态 relocation sentinel；
服务端只用当前 Mapping 及由槽位派生的模板边界重新解析该位置，不把它持久化成玩家坐标，也不恢复原坐标。

房车模板来自 2026-09-25 服务端日志，保留了 357 个原始对象的坐标、对象类、名称、sprite、
朝向及捕获状态。捕获数据中的 50 处栅栏原有墙体衬层，其中 4 个不在房车边界上的衬层已移除；
其余 46 处真实边界位置上的 47 个木墙对象只在客户端隐藏；(2,2,0) 有两面同向墙。
墙体碰撞仍由服务端保留。
隐形墙现用于围住可活动区域，角落不再放独立隐形障碍物；西北角同时有北墙和西墙，另有四段角落隐形墙补齐边界缺口；当前共 412 个模板对象。玩家活动范围为 walkAabbs 描述的 6×23 格。
沙盒选项“允许在火车机电区域建造”默认关闭：关闭时保留驾驶室内部 x=-4..1、y=-2..1 的 24 个 z0 建造格；开启时新生成的房车使用单独注册的机电区域模板，开放区精确等于 z=1 屋顶格向 z=0 的 88 格投影，由五个不重叠的预定义矩形组成。驾驶室、短机头和长机头中没有屋顶的走廊格仍可通行，但不能建造或拆除，受保护的模板对象会按原模板恢复。生成时所选模板 ID 保存在 mapping record 中，因此更改选项只影响之后生成的房车；已有房车继续使用其记录的布局。16 个水代理的 3×3 搜索范围覆盖全部 88 格；发电和供水系统部件仍按各自角色保护。服务端每 10 tick 对
100×100 管理范围内的玩家采样，以玩家为中心将 3×3 XY 坐标去重排入共享的有界恢复队列。
每 tick 通常检查一个 XY 坐标；积压超过阈值时预算增至 2 或 4 个，并核对该坐标的受管 Z 层。
没有匹配在线玩家的队列项会出队丢弃；卸载或缺失的格不会强制加载。外部玩家物品和归属不明对象保留。
模板对象在未开放建造的格子被拆除后，会在玩家接近并处理到该坐标时补回；开放建造的 z0
格不自动
恢复。上层按捕获内容生成，不补齐空白格。实际边界 ledger 记录 59 条捕获墙边；西北角
由北墙和西墙组成，另新增四段隐形墙补齐活动区域边界缺口。移动许可按模板 walkAabbs 判定，
建造许可按 buildCells 判定；服务端边界守卫使用当前映射和玩家位置。

玩家可从房车机车右键菜单请求认领房车安全屋。服务端按当前 utility record 结算后检查水箱、供水泵、
滤芯剩余量和供水泵电力；中心水箱当前水量为零不影响认领，认领后水系统状态变化也不会撤销安全屋。
安全屋使用原生 SafeHouse，范围是当前 mapping anchor 对应驾驶室的单个 6×4 XY 矩形
（相对坐标 x=-4..1、y=-2..1），不扩展到机电区或走廊。安全屋的原生驱逐与释放行为保持原样；
首次进程内创建的原生安全屋缺少聊天频道时，释放仍可能在完成删除和客户端同步后报频道不存在。

三条机制使用不同名称。**边界守卫（BoundaryGuard）**按服务端权威位置和 RV AABB 跟踪玩家，
并将越出管理范围的玩家送回已验证的 RV 入口位置。**模板保护修复（TemplateProtectionRepair）**
检查并恢复当前 RV 模板中受保护的对象；对象清理仍要求当前身份和模板归属明确。**屋顶刷新
（RoofRefresh）**在进入房车和重连路径上按当前身份尝试刷新房间与屋顶元数据；刷新时可临时
添加并移除未标记地板，保留模板地板。**墙体重载（WallReloadProtection）**处理特定外墙移除
后的独立流程：服务端捕获当前在场成员，协调临时远移、chunk 周期及逐人返回；客户端异步
传送完成后用 token ACK 推进阶段。客户端不提交可信坐标。

## Schema 与模块接口

全包使用 Lua 中集中声明的单一 schema 版本号，并保存到 ModData。启动时只比较一次：匹配时继续，
不匹配或缺失时发出警告但继续运行。各模块默认 ModData 与接口符合当前定义，不增加重复版本检查、
结构防护、接口校验、兼容、迁移或回退分支。用户承诺不使用旧存档；运行错误由游戏正常抛出，
之后由人工或 agent 排查是否与 schema 版本有关。

本模组生成的模板、ModData、mapping、utility record 和进程内状态按当前定义视为可信。理论上不可能的
内部状态直接暴露为异常；不为代码缺陷、人工改档、恶意篡改或磁盘损坏添加修复、默认值、兼容或恢复分支。
客户端只发送操作意图，服务端依据当前世界状态执行验证与变更；依赖 Project Zomboid 提供的可靠有序传输，
不额外增加丢包、重复包或乱序协议层。

## RV 水电管理

水与电在房车管理面板中使用独立选项卡，操作由各自的服务端状态处理。供电改动不改变水系统规则。

### 供水系统

水界面分“水系统部件（必须）”和“水系统部件（可选）”。必要部件是最多两只房车水箱、不可拆除的
管道加压泵和水过滤器；水箱每只容量 1,000 L，加压泵运行需 20 W，过滤器标称过滤能力为 5,000 L。
缺少必要部件、加压泵未获得电力或过滤器耗尽时，界面分别显示对应异常状态。安装水系统部件时界面
显示操作进度。

可选部件是抽水泵和雨水收集器。小型水泵的抽水速率为 40 L/min、功率 20 W；工业水泵为 200 L/min、
功率 100 W。安装抽水泵后，玩家可在房车旁、处于车外且未坐在座位时，携带橡胶软管从附近天然水源
选择加水；缺少软管、电力或附近天然水源时，菜单会给出对应提示。服务端按当前车辆、玩家位置、库存、
电力及世界水源状态处理请求。可选雨水收集器分别记录容量与当前雨雪水量。

从容器手动加水按 40 L/min 结算。天然水源菜单优先列出搜索范围内全部干净水源；污染水源至多列出一项，
有无限水源时选择其中一处，否则选择余量最大的一处。该菜单和天然水源操作在本轮正式化后尚未完成
运行时复核。

房车水箱、水过滤器和水泵都是物品，不是建造建筑。水箱配方图标使用独立的 `RailroaderRV_WaterTank`
图标；各物品与配方纹理通过 RailroaderRV 前缀隔离游戏本体和其他模组的同名资源。

## 房车供电

每个 RV generation 的 mapping record 保存其模板 ID；屋顶几何只定义在模板里，UtilityStore 不复制模板数据。
UtilityStore record 保存必要的当前系统状态：安装的发电机及其启停、
油箱与虚拟燃油、电池组荷电量、充电器、逆变器、智能控制器、当前设备快照，以及唯一的
`lastSettlementTime`。设备快照只有模板固定设备和玩家 `buildCells` 内设备的两份最新列表，用于结算和跨
重启传递当前状态；不写 IsoObject 或区块 ModData，不记录操作历史、扫描历史、历史负载或待补结算债务。
新 RV 默认没有逻辑发电机、油箱、电池、充电器、逆变器或控制器；
虚拟油量和电池电量均为零。系统不把世界重启前的时间单独追溯结算。

房车按 UPS 方式运行：燃油发电机只给电池组充电，用电器只从电池组取电。充电器和逆变器未安装时，
对应效率为空，不使用默认 90% 等数值参与计算；缺少充电器时不能充电，缺少逆变器时不能放电，
没有电池时两者都不能进行。已有电池电量在缺少发电机或充电器时仍可经逆变器放电；发电设备可在
缺少逆变器时继续给电池充电。

一次结算发生在每游戏 10 分钟、进入或离开 RV、以及玩家修改供电系统时。每个 RV 进程内只保留一份
最新设备快照 `oldList` 和一个 `isInitialized` 标记；标记只在内存中，不持久化。进程首次需要结算或展示
该 RV 负载时，直接从当前 UtilityStore 完整 record 的 `power.deviceCache` 恢复快照。新建 RV 的完整 record
已带有两张空表和当前 `lastSettlementTime`，不继承其他 generation 的快照；已有 record 必须带有这两张缓存表，
缺失时会暴露内部状态错误，不按空表继续。

结算先检查模板固定设备和玩家建造区域所需的全部 chunk。只有区域完整加载时，才按模板坐标读取固定设备，
并在模板 `buildCells` 中全量扫描玩家建造设备；成功结果替换唯一的 `oldList`，立即覆盖保存在全局
UtilityStore 完整 record 中的缓存字段。扫描只更新当前候选 record，不单独传输 ModData；扫描和结算成功后，
由一次完整 record commit 连同新缓存统一持久化。部分或未加载时沿用 `oldList`，不把缺失区域解释为零负载，
也不提交残缺扫描结果；安装等定时操作沿用既有拒绝路径保存按旧缓存计算出的 settlement baseline。模板固定对象暂时缺失时
沿用该对象快照中的上次状态；没有上次状态时按关闭处理。设备请求状态与实际获电状态分开记录。

随后按最终 `oldList` 和修改前的供电系统状态，近似计算整个未结算时间段；直接 clamp 虚拟燃油与电池电量，
更新唯一的 `lastSettlementTime`，同步原版供电代理并保存当前状态。成功扫描的新快照只覆盖前一份，不记录
扫描时刻或历史列表。结算期间不追溯设备开关时刻、油尽、满电、空电或控制器阈值跨越；扫描和结算的误差
由后续常规结算自然反映，不回放负载或补偿历史操作。
安装、拆卸使用服务端权威的定时动作；槽位、容量、物品和供电状态都在服务端完成阶段复查，只有通过后才消费物品。加油逐段结算并转移，取消时已完成的部分仍然保留。分段边界造成
超量时，虚拟油量直接限制在总容量，已从油桶转出的燃油不会退款。安装完成处理时按最近的已保存负载结算旧系统至当前时间；成功后只做一次完整扫描，按新状态结算、检查过载并提交。普通业务条件失败时不消费物品，并广播当前状态。

玩家最多安装 32 台发电设备（含太阳能板、风力机和燃油发电机）、8 个油箱和 16 块电池。游戏内燃油机映射为：`Base.Generator_Old`
（老式，3 kW，基础油耗 0.15 L/游戏小时、发电系数 1.35 L/kWh）、`Base.Generator` 与
`Base.Generator_Blue`（普通，4 kW，0.10 L/小时、1.25 L/kWh）、`Base.Generator_Yellow`
（高级，5 kW，0.08 L/小时、1.15 L/kWh）。这些是本模组的设计参数。每台机组的实际出力按其额定
功率比例分配；总出力不超过电池侧需求或所有可运行机组的额定功率之和。开启机组的油耗为基础油耗
加上实际发电功率（kW）乘发电系数；关机机组不耗油。启动需要存在油箱和虚拟燃油，控制器会在
结算后统一启停全部燃油机：电池荷电低于 10% 时启动，高于 30% 时关闭。系统操作完成后也会按
当前荷电状态评估控制器，让结果用于之后的运行；操作前经过的时间始终按修改前的机组状态结算。

### 屋顶虚拟设备

每个共享模板显式保存屋顶格的相对 `x/y/z`，当前 mapping 的模板 ID 决定使用哪组格子。当前模板的 88 个格来自捕获屋顶覆盖对象的顶层坐标，
因此只显示实际覆盖区域；不是由屋顶外接矩形补出的空格。每格最多安装一台设备：燃油发电机、
太阳能板、风机或雨水收集桶。风机和太阳能板与雨桶之间按同层八邻格双向限制。服务器用当前
RV 模板、已保存设备和玩家库存重新判定格子与类型；界面提交的格子只是安装意图。

安装和拆除都用 150 tick 定时动作，只在完成时修改状态和物品；动作中断不消耗物品。发电设备
仍保存在 `power.generators` 中，并额外保存模板相对坐标。集水状态独立保存在 UtilityStore 的
虚拟 `water.roofCollectors`，不创建世界对象或水路代理。安装物品只接受配置的雨水收集桶 Moveable sprite
及其闭盖变体，不接受普通 `Base.Bucket` 或其他容器。每条集水记录保存原 Moveable factory type、流体容器
容量、容器名、rain-catcher 属性和虚拟水量；目标区域完整扫描成功且当前下雨时，每个 10 分钟事件增加 4 L，
并按该桶记录的容量封顶。拆除时按记录的 factory type 重建雨桶，并恢复其流体容器属性；虚拟水量随设备记录移除。

屋顶窗口和8邻格规则位于独立 Roof 模块；服务端只在原生动作完成时重查当前房车、模板屋顶格、设备约束和玩家库存。服务端记录与库存型屋顶操作可在当前 resolver 确认的房车身份范围内从房车外侧执行；目标区块可访问时进行负载扫描和原生发电机刷新，不可访问时跳过对应扫描和刷新，但服务端记录结算及设备事务仍照常提交，并在成功后广播屋顶设备快照。

九种 `Base.SmallGasTank1..3`、`Base.NormalGasTank1..3` 和 `Base.BigGasTank1..3` 油箱从物品脚本读取
容量与已有汽油；容量同时应用原版耐久度影响。所有油箱组成一个虚拟总容量，不单独模拟箱内燃油。
拆除油箱时按它占总容量的比例退还虚拟汽油；拆除最后一个油箱会将剩余汽油全部装回返还物品。

电池组参数按每块电池状态计算后求和；当前基础配置为 720 Wh 容量、250 W 最大充电功率和 1500 W
最大放电功率，耐久度会分别影响可用容量、充电功率与放电功率。充电需求为各电池充电能力之和，
满电时按电池侧放电功率补偿，并计入充电器效率。设备状态读取支持灯、收音机/电视、冰箱/冷冻柜、
洗衣机/干衣机及组合或堆叠洗烘机、炉灶和微波炉；用电负载超出电池与逆变器可提供的功率时，
原版 generator 代理不会给超额负载供电。

模板内的原版 generator 仅是实际供电代理，不代表一台逻辑燃油机，也不进入虚拟油耗或发电统计；
代理的原版燃油和耐久度由服务端维护，以避免原版状态另行耗油或导致断电。玩家安装的逻辑燃油机
拆卸后保留物品名称、耐久度、使用状态和原生 `ModData.fuel`；该原生字段不会参与虚拟油箱结算。
智能控制器要求电工 7 级；配方需要电线 20、电子废料 100、红绿灯泡各 1、小金属板 6、铜废料 10、
铝废料 10 和一台台式电脑。螺丝刀为保留工具，不再需要汽车电池充电器。

### 太阳能与风力发电计算

太阳能面板每块额定 250 W，风力发电机每台额定 400 W。服务端按当前世界时间和气候采样：
日内小时 `h` 使用 `GameTime:getTimeOfDay()` 的小数小时；日历月份 `m` 使用
`GameTime:getMonth() + 1` 转为 1–12；云、总降水（包括雪）和雾强度分别来自
`ClimateManager:getCloudIntensity()`、`getPrecipitationIntensity()` 和 `getFogIntensity()`；
风速（km/h）来自 `getWindspeedKph()`。

太阳能日照系数和天气后的单板可用功率为：

```text
D = max(0, 1.2 × sin(π × (h − 6) / 12))
Y = 0.75 + 0.35 × cos(2π × (m − 7) / 12)
I = D × Y
单板可用功率 = 250 × min(1,
    I × (1 − 云强度 × 0.5)
      × (1 − 总降水强度 × 0.3)
      × (1 − 雾强度 × 0.2)) W
```

风机按风速分段计算：

```text
v < 10                 → 0 W
10 ≤ v < 45            → 400 × (v³ − 10³) / (45³ − 10³) W
45 ≤ v < 90            → 400 W
v ≥ 90                 → 0 W
```

两类设备通过屋顶虚拟摆放窗口选择格子，安装时启用并占用发电机槽位；它们不需要虚拟燃油，
不计燃油消耗，也不应用耐久度或网络加成。每个结算时点先将太阳能和风能
的公式输出用于当前充电需求，剩余需求再由启用的燃油发电机补足。快照中的
`renewableAvailablePowerW` 是公式输出总和，`renewableUsedPowerW` 是送入充电器前实际使用的
可再生功率，`generationPowerW` 是所有发电设备送入充电器的功率；最终电池侧功率
`batteryChargePowerW` 还会应用充电器效率和电池最大充电功率。因此满电、没有负载或充电器未安装时，
公式可用功率和电池实际吸收功率可以不同。现有燃油机、电池、充电器和 UPS 结算规则保持有效。

## 验证状态

本次 RailroaderRV 1.0 文档和正式化事务没有启动游戏、客户端、服务器或运行时测试脚本。下列离线行为检查
可以从项目根目录运行，使用 Lupa 执行 Lua 模块；它们不替代一键多人游戏测试：

```powershell
python -m pip install lupa
python -m unittest discover -s RailroaderRV/tests -p "test_rv_installation_flow.py" -v
python -m unittest discover -s RailroaderRV/tests -p "test_rv_power_device_cache.py" -v
python -m unittest discover -s RailroaderRV/tests -p "test_rv_generation.py" -v
```

实际联机验收的唯一入口为项目根目录下的 `python testserver/run_test.py`；它会启动可见的服务器控制台和
常规客户端，不应拆开启动两者。脚本会生成服务端 `Mods=BuildingCraft;RailroaderRV;B42Trans_CN`、
`WorkshopItems=3556544454` 配置；该 Workshop ID 对应统一原版汉化 `B42Trans_CN`。客户端 cache 不单独
保存模组列表，连接后按服务器的模组配置加载。脚本每次启动会重写
相关 Mods/WorkshopItems 设置，因此手工配置会被覆盖。此 README 不推断 Railroader 的 Workshop ID。

已反馈的 15 L 饮水桶曾出现 0.6 L 差值；后续一轮连续加水得到 15、30、45 L，未复现该差值，仍不视为
RailroaderRV 1.0 的实机验收结论。新的天然水源菜单行为同样尚未实测。此前屋顶刷新在未加载的模板位置
报告无法刷新；日志未给出 Lua 异常，根因仍待定位。

2026-09-15 的历史人工测试曾报告拆墙、进出和补墙成功，但东/南墙格可建地板、东墙格可建
北墙仍待未来实机复核。当前源码包含相应 host 处理，尚无实机证据确认问题已解决。后续
人工测试不要要求用户提供客户端界面无法显示的实际坐标。
