1. `ctx.playerPositionInRegion` 在全树**没有任何生产者**：字符串 `playerPositionInRegion` 在整个工作区命中 18 处，唯一的字段写入是 [RV_RailroaderServer_Mapping.lua:155](../../contents/mods/RailroaderRV/42/media/lua/server/RailroaderRV/RVMapping/RV_RailroaderServer_Mapping.lua:155)——它把该函数注入 **BoundaryValidation 的子 ctx**，而不是 adapter 门面 ctx（[RV_RailroaderServer.lua:95-108](../../contents/mods/RailroaderRV/42/media/lua/server/RailroaderRV/Core/RV_RailroaderServer.lua:95)）。本文件的 [RV_RailroaderServer_WallReload.lua:30](../../contents/mods/RailroaderRV/42/media/lua/server/RailroaderRV/WallReloadProtection/RV_RailroaderServer_WallReload.lua:30) 因此绑定 nil。**条件性推断**：L74 的 `playerPositionInRegion(player, area)` 会以 nil 调用抛错，除非存在本树之外的运行期注入。
2. `RailroaderRV.Server.isGenerationTransactionActive` **没有任何生产者**：全树命中 7 处（`RV_RailroaderServer_Sentinel.lua:153/157/201`、`RV_UtilityServer.lua:73/74`、本模块 `RV_WallReloadProtection.lua:456/460`），全部是读取或类型探测；没有 `function RV.Server.isGenerationTransactionActive` 声明，也没有 `RV.Server.isGenerationTransactionActive = ...` 赋值。**条件性推断**：`M.begin`（L456-L458）会恒返回 `false, "RV generation transaction state is unavailable"`，即当前源码下外墙重载操作无法启动。该结论与同批独立报告 [server-Core.md](server-Core.md) 接口边界问题 #1、[server-Construction.md](server-Construction.md) 第 195 行一致。`tests/test_rv_server.py`（L1891）仍断言该函数存在，但同一断言块还要求 `isRoofRefreshTransactionActive`、`pendingWallRoofRefreshes` 等已退役符号，属陈旧测试，不作为「生产者存在」的证据。
3. 本模块**不访问** `Boundary._states` / `Boundary._tick`：对 `BoundaryGuard` 的两个文件检索这两个符号为 0 命中，本模块只经 `boundaryForPlayer` / `boundaryFor` / `isCurrentShellWall` / `beginTransition` / `extendTransition` / `completeTransition` 这些公开发布的方法交互（证据见第 5 章）。

## 目录职责与清单

本目录是**两层结构**：`RV_RailroaderServer_WallReload.lua` 是挂在 RailroaderServer adapter 上的**检测/触发/发布层**——它决定「哪个被移除对象是当前 RV 的外墙」、把该决定翻译成一次重载操作、并在操作成功后调用 RoofRefresh；`RV_WallReloadProtection.lua` 是**操作服务层**——每 `rvId:generation` 一张内存操作表、四相位状态机、边界租约与客户端确认，不持有队列、重试账本、持久化事务或每成员尝试计数（L27-L30 注释）。

## 模块间复用、提取和职责拆分

### 已有共用与可提取机会

- **通用 Java/数值调用已经复用，不要再造第二份**：服务层全部经 [RV_ServerUtil.lua](../../contents/mods/RailroaderRV/42/media/lua/server/RailroaderRV/Common/RV_ServerUtil.lua)（`integer`/`invoke`/`callSucceeded`/`callGlobalSucceeded`/`toNumber`/`isFiniteNumber`，RV_WallReloadProtection.lua L14 引入），没有本文件私有的 pcall 调用封装；权威传送复用 `RV.Server.teleportToPosition`（Common/RV_ServerTeleport.lua L5，经 RV_Server.lua L138 转出）而不是自己写 `teleportTo`。判断：现状正确，无需提取。
- **可提取项 1（价值最高）：统一「谁在这辆 RV 里」的定义。** 现状是两份实现：文件一 L62-L99 用 `RegionSlots.indexToRegion(record.slotIndex)` 的整块区域包络 + `map.players`/`record.players` 双向 `inside` 证明，只用于「有没有权威玩家」的门与日志；服务层 L403-L440 用 `boundary.managed` 的 100×100×Z 半开区 + onlineId，产出真正的成员与回位坐标。差异是实质性的：区域包络严格宽于 managed 边界，因此两份实现可以在同一时刻给出不同结论（包络说「有人」，服务层说「没成员」）——此时门放行、`begin` 拒绝，只有日志能看出原因。**净收益**：删掉文件一的重复门后，「车内有谁」只有一个定义，`insidePlayersForRecord` 未使用的 `player`/`originalPosition` 字段与它唯一的 nil 调用点（L74）一并消失。**成本**：服务层需把「拒绝原因」说清楚（`begin` 已经返回 `"no authoritative player is inside this RV"`），或新增一个 `WallReload.membersFor(rvId, generation)` 查询供调用方打印。建议：先做「删除重复门」这一最小步骤，收益与成本比最高。

- **RV_WallReloadProtection.lua（508 行）不建议再拆。** 它是一台单一状态机：身份/租约/前置判定（L36-L206）+ 操作生命周期（L208-L335）+ 三个公开入口（L337-L505）。三段共享同一个闭包私有状态 `operations` 与 `lastTick`（L21、L34）；按相位或按「支撑函数/公开入口」切开就必须把这些私有状态变成跨文件导出，接口面反而扩大，而调用方向（begin → onTick → onComplete）没有任何分支会只用到其中一段。**唯一可议的缝**是「成员捕获 + 活体重绑」（L183-L221、L403-L440）：它是纯函数（boundary + 在线快照 → 成员），也正是与文件一重复的那部分；若采纳可提取项 1，应把这部分作为「RV 占用查询」独立成一个小模块，而不是在本文件内部再分层。
- **RV_RailroaderServer_WallReload.lua（311 行）建议拆出一块。** 该文件由两种职责粘合：①外墙移除检测 → 操作启动（L128-L240），②客户端 stale-room 监视器周期重挂（L37-L44 的 `armRoomOwnership` + L284-L309 的 `rearmRoomOwnershipMonitors`）。②与墙体重载零语义重叠（它服务于 RoomOwnership 的 room guard），目前挂在墙体重载文件里只因为这职责是从已退役的屋顶刷新采样器继承来的。**边界与成本**：把这两个函数搬到 RoomOwnership（或 Core 的 tick 路径）+ 改 [RV_RailroaderServer_Tick.lua:65-67](../../contents/mods/RailroaderRV/42/media/lua/server/RailroaderRV/Core/RV_RailroaderServer_Tick.lua:65) 的一处调用即可，无行为变化。建议：**是**，这是本目录最干净的拆分。

### 接口边界问题

- **【高优先级，源码事实 + 条件性推断】`M.begin` 的 generation 互斥前置没有提供者。** L456-L458 在 `api.isGenerationTransactionActive` 不是函数时直接 `return false, "RV generation transaction state is unavailable"`；全树检索该符号命中 7 处，**全部是读取**（本模块 2 处、Sentinel 3 处、UtilityServer 2 处），没有生产者。条件性推断：外墙重载操作在当前源码下无法启动，`wallReloadForObject` 会打印 `wall reload not started room=... detail=RV generation transaction state is unavailable`。姊妹查询 `isWallReloadTransactionActive` 由本模块 L256 正常发布，说明机制本身可用，缺的是 generation 一侧的转发（真实状态在 `GenerationTransaction.isActive()`，只在 GenerationFlow L327 被模块内使用）。修复方向属 Core 侧（在 RV_Server.lua 或 GenerationTransaction 处发布），**不在本模块范围内**；本模块的正确做法保持「查询缺失即拒绝」的 fail-closed 口径不变。
- **【高优先级，源码事实 + 条件性推断】`ctx.playerPositionInRegion` 无生产者**（文件一 L30 → L74）。它使文件一的两个入口（`onObjectAboutToBeRemoved`、`onDestroyIsoThumpable`）在成员捕获阶段抛错，而不是走「无可信玩家」的良性拒绝路径。可选的消除方式：采纳第 4 章可提取项 1，直接删掉这段重复门——那样本模块就不再有这个悬空依赖，同时消除两份「谁在车内」实现的分歧；若保留该门，则应先把它接到一个真实存在的坐标谓词上。
- **两套「墙」判定的分工是刻意的，但要写进合同。** `cheapShellWallCandidate`（文件一 L128，独立实现）与 `Boundary.isCurrentShellWall`（DemolitionProtection 所有）构成「廉价候选 → 权威判定」两级谓词：前者只回答「看起来像不像本 RV 的墙」，后者要求完整账本条目与模板属性一致。当前两级各有一份角色/标签知识（可提取项 2）。这不是隐藏耦合（走的是公开函数），但存在**规则漂移**风险：只改一侧会让候选门拒绝本应成立的墙（漏检）或让权威判定成为纯开销。
- **`M.acknowledge` 的三值协议必须按形状消费。** `true, true`（接受）／`true, false, reason`（token 属于本操作但发送者不是成员）／单个 `false`（token 不属于本操作，必须继续 generation 分支）。GenerationAck L26-L28 的 `if wallHandled then return wallAccepted, wallReason end` 是正确消费方式；把首返回值当布尔用会吞掉 generation 的 relocation ack。
- **无重试、无队列、单 deadline 是有意设计，但失败语义不对称。** 服务层只有 `OPERATION_TIMEOUT_TICKS = 600`（L25）一个总预算，没有每成员尝试计数、没有队列、没有持久化事务（L27-L30）；失败路径 `finishFailure` 只做一次尽力回位，失败成员不再被跟踪（其租约等 TTL 过期）。另外：**成员全部离线时**（L346-L349）操作被「弃用」而不是失败——不发送回位、**不触发 onComplete**，日志只有 `abandoned ... reason=no-member-online`。条件性推断：这种情况下外墙对象已被真正移除，而屋顶/房间重算不会被本回调触发，需要依赖后续的进入/重连刷新路径（[RV_RailroaderServer_Mapping.lua:172-194](../../contents/mods/RailroaderRV/42/media/lua/server/RailroaderRV/RVMapping/RV_RailroaderServer_Mapping.lua:172) 的 `refreshRoofForPlayer`）或重新生成来收敛；这是当前设计里最需要运行时验证的一条失败路径。
- **多 RV 并发没有被显式禁止。** `M.begin` 只拒绝同键（L451-L453），不检查其它 rvId 是否已有操作；`M.isWallReloadActive(nil)` 的进程级答案只被外部消费方（Enter/Exit、generation 排队、utility、房间归属）用来阻塞自己，不阻止第二次 `begin`。注释 L19-L20 的「the single managed world scope never runs two」是设计假设（一个世界范围只对应一辆 RV），不是代码约束。条件性推断：若同一世界范围真的出现两个 `rvId` 同时触发墙体重载，两次操作的成员集合与边界租约互不感知（`RegionSlots` 支持多槽位）。建议（若多 RV 是现实场景）：在 `M.begin` 增加「已有任一操作即拒绝」的显式判断，或在注释中把该假设升级为合同。
- **语义残留的两处命名。** ①BoundaryValidation 在被墙体重载拒绝时打印的诊断原因是 `"roof-refresh-transaction-rejected"`（L144）——名字来自已退役的屋顶刷新事务，日志读者会误判拒绝来源。②`Constants.ROOF_REFRESH_REMOTE_OFFSET_*` 被墙体重载复用（第 4 章可提取项 3）。两者都不改变行为，但都会持续误导。
