# RailroaderRV server Lua

- `RV_Server.lua` composes the server event handlers and generation transaction modules.
- `RV_RailroaderServer*.lua` handles server-authoritative Railroader entry, exit, mapping, and transition validation.
- `RV_BoundaryServer*.lua` implements bitmap-scoped boundary tracking, transition leases, sweeping, and object cleanup.
- `RV_Server_*.lua`, `RV_ServerSchema.lua`, and `RV_ServerWorld.lua` provide generation, persistence validation, and world operations; `RV_Utility*.lua` and `RV_RoofRepair.lua` provide utility and repair services.
- `RV_Server_RoomOwnership.lua` repairs invalid RoomDef references with synchronous transaction scans, an authoritative current-square check for online players each tick, a 3x3 neighborhood probe every 120 ticks, and merged object-event scans with bounded delayed rechecks. Full scans require every expected structure square to be loaded; incomplete scans remain unconfirmed.
- Generation waits at the staging point while the base footprint and wall squares load. Upper roof squares are created one at a time in `ROOF_FLOOR`; the first required full RoomDef scan runs after that loop and before final relocation. If generation fails before the roof loop completes, rollback strictly scans the old footprint and base/wall squares plus only upper squares already materialized in the transaction cell. Once the roof loop completes, rollback requires the full new roof too; missing required squares keep rollback failed.
- Keep world changes authoritative on the server, accept client intent only, and reject persisted data that does not match the current declared schema.
- TEMPORARY `[RailroaderRVTest][PerfTrace]` summaries in `RV_Server_RoomOwnership.lua`, `RV_BoundaryServer_Sweep.lua`, and `RV_UtilityServer.lua` emit about once per aligned 10-second window, labeled with Unix epoch seconds from protected `os.time()` calls. If that clock is unavailable at module load or errors later, tracing is disabled. They distinguish roomguard coordinate probes/full scans, cleanup square/object visits, and utility tick/failure counts; full scans, cleanup batches, utility settlements, and mapping syncs report total/peak elapsed milliseconds when protected `getTimestampMs()` calls succeed. Remove these counters after CPU correlation is complete.
